# Standardized researcher script

Edit the immutable protocol's study information and contact before issuing pilot/main sessions. Keep institutional review/approval details accurate and editable; none are supplied or implied by the software.

1. **Setup:** “This is a study of digital checking tasks with different interface configurations. Please silence personal notifications. Use this mouse or trackpad throughout, keep the study window visible, and work accurately and steadily.” Use the same Chromium version, display/zoom, input device and quiet setting for everyone. Record browser/OS, viewport and display setup in a session annotation. Check 1280×720 CSS pixels or larger at the intended zoom; do not suppress zoom.
2. **Consent:** Present the approved local information, eligibility rules, 20–25 minute planning estimate (extra practice/rest may take longer), voluntary withdrawal and retention policy. Explain whom to contact and how the completion identifier is used. Do not invent institutional approval. Answer consent questions before timed work.
3. **Training:** “Compare Product code, Batch code, Quantity, Packaging, Delivery code, Shipping service, Dispatch date, and Seal code in that order, top to bottom. Select a category with the button at the left of its row, choose Matches or Does not match, then Submit check. The packaging rule table stays visible. Finish order when you are done. Secondary tasks and progress reminders may occur; the order returns automatically.” Use the same worked example and all three demonstration orders for everyone, then the configured assessed practice. Let the interface provide the same explanations. Record assistance. Failure to meet the criterion ends training without a main allocation; do not coach someone through a hidden exception.
4. **Main blocks:** “Work accurately and steadily.” Do not mention A/B/C or hypotheses, cue benefit, expected harm, target speed or scores. Do not tell the participant which check is next. There is no factual correctness feedback. Do not exclude poor performers retrospectively.
5. **Problems/assistance:** If assistance, external interruption or an unscheduled rest is needed, use **Pause / report a problem** immediately, select the reason on the pause screen, then Resume when ready. Explain only procedural/technical matters, without repairing progress history. Add a permanent researcher annotation with session ID, block/order/event sequence if known, what happened, whether timing boundaries were captured, and whether any content advice was given. Late reports are annotations; do not invent precise timing or subtract estimates silently. Blur, hidden tab, resize and reload are automatically recorded. A disrupted secondary task is not replayed. Never refresh to rerandomize or erase an error.
6. **Ratings/breaks:** “Rate the whole preceding block, including secondary tasks where present. On Performance, the left end means Perfect and the right end means Failure.” (pilot-2 sessions: “0 means Perfect and 100 means Failure.”) Do not interpret responses or reveal performance. Each block's ratings precede the two fixed 60-second breaks. Do not shorten these breaks; additional rest is logged. Withdrawal remains possible.
7. **Completion:** Wait for server acknowledgement. Confirm collection completeness and technical health, not whether the cue effect is favorable. Preserve raw ZIP exports and backups by protocol/mode. Mark demonstrations and technical runs synthetic. Never use pilot or automated data as main participants.

Pilot-4 eligibility and review rules are specified in [analysis.md](analysis.md). Record recruitment/consent/training attrition without using performance to decide retrospective inclusion. Earlier started sessions use their original script and protocol. Teammates use demo/synthetic sessions on their own local databases; never merge these databases into main collection.
